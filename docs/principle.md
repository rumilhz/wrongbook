# 原理详解：为什么「前置防错」优于「事后纠错」

## 1. 问题：Agent 的纠错是免费的，但不是无代价的

大语言模型 Agent 遇到报错时，几乎总是能自己分析、自己修复——它不缺**纠错能力**。
但每次纠错都要消耗：

- **时间**：多一轮"报错 → 分析 → 重试"的往返
- **token**：读报错输出、推理根因、重写命令，通常 2-5 倍于正确写法的成本
- **可靠性**：修复往往引入新问题，形成"修了 A 坏了 B"的级联

真人学习的类比：老师告诉你"这个公式别这么套"，你就不会错——省掉的是
"做错 → 发现 → 重做"整个环节。**Agent 也应该有"老师"，而且应该在动笔之前。**

## 2. 核心洞察：被动检索无法实现"写之前防错"

这是本方案区别于所有"经验/记忆"类方案的根本点。

### 长期记忆的检索是**被动**的

常见的记忆机制（mem0、MemGPT、平台记忆、lessons 数据库）都是：
- 索引/描述常驻（每会话加载）
- 正文**按需检索**——通常靠关键词或语义相似度命中

问题在于：**"写之前"这个时刻没有检索触发信号**。
- 出错后，报错文本里有关键词（`exit code`、`failed`、具体报错），检索自然命中；
- 但准备写命令时，脑子里还没有报错文本，唯一能检索的输入是"我要做 X"——
  而"做 X 的正确写法"和"做 X 的错误写法"在语义上高度相似，检索常常不命中，或命中了也未必被当作"禁则"读取。

结论：**被动检索只能支撑"事后查字典"，支撑不了"事前预防"。**

### 常驻指令是**主动**的

`AGENTS.md` / `CLAUDE.md` / `REASONIX.md` 这类指令文件是 **cache-stable prompt 前缀**：
每个相关 turn 都在上下文中，不需要任何检索触发。

因此，要保证"写之前"规则在场，唯一可靠的机制是**常驻指令**。它的职责不是装下所有规则，
而是装下一条**元规则**：

> 每次执行命令/写代码/装包之前，先检索错题本核对禁则。

元规则每轮都在 → 每次动手前都会被读到 → 触发一次对错题本的检索 → 禁则生效。

## 3. 为什么记录格式是「禁止 X —— 因为会 Y」

三段式复盘（为什么出错 / 如何解决 / 如何避免）是直觉的选择，但分析一下 token 的边际价值：

| 信息 | 对未来复用的价值 | 判断 |
|---|---|---|
| 如何避免（预防性写法） | 高——直接可执行 | **保留，作为主体** |
| 为什么出错（根因） | 中——用于判断"变体场景是否同类" | **压缩成一行** |
| 如何解决（修复过程） | 低——下次根本不该走到这一步 | **默认丢弃**，有非显然的坑才留备注 |

所以一行式 `禁止 X —— 因为会 Y` 是 token 效率与复用价值的平衡点：
- 短 → 可扫描、可常驻到高频铁律区
- 「禁止 X」是**可执行指令**，不是知识
- 「因为会 Y」一行保住适用边界，防止"换个写法就不认了"

## 4. 为什么指令文件必须短（双层隔离的理由）

### token 成本：常驻文件的每一行，每个 turn 都要付

```
每 turn 成本 ≈ 指令文件行数 × 每行 token × 会话 turn 数
```

一条禁则约 20-40 token。放 50 条进常驻文件 = 每 turn 多 1000-2000 token，
一个长会话多付几万 token。

### 效果成本：规则膨胀会失效

Claude Code 社区反复报告的教训（见 docs/comparison.md 引用的案例）：
**规则写了几百行之后，Agent 反而无视规则**。原因有二：
1. 上下文里规则密度过高，模型注意力被稀释；
2. 规则之间互相矛盾/过时时，模型学会了"选择性忽略"。

### 结论：双层结构

```
┌─────────────────────────────────────┐
│ 常驻指令文件（≤30 行，每轮加载）          │
│   - 1 条元规则（写之前查错题本）          │
│   - ≤5 条最高频铁律（最痛的坑兜底）        │
└─────────────────────────────────────┘
                 │ 元规则触发检索
                 ▼
┌─────────────────────────────────────┐
│ 错题本（记忆 / lessons.md，按需检索）     │
│   - 完整禁则清单（可以几百条）            │
│   - 分类组织，一条一行                    │
│   - 同类第二次出现 → 扩充单条             │
└─────────────────────────────────────┘
```

## 5. 执行率兜底：常驻指令仍不够，需要三层补强

> 现实检验（2026-08）：全局指令文件**已加载**在上下文中，Agent 执行命令时仍可能直接动手、
> 跳过"先核对"。原因：LLM 遵守指令是**概率性**的——任务繁忙时"直接跑命令"的胜率高于
> "先查一次错题本"。纯文字指令做不到 100% 确定性执行。这是本方案承认的边界，也是
> 以下三个兜底设计存在的原因。

### 5.1 可见核对动作（行为监督）

把"核对"从**心里想想**变成**输出可见**：

> 每次调用 shell 工具前，回复先写一行 `[错题本核对] 领域=xx 无命中 / 命中禁则xx→改用yy`

模型如果跳过，用户肉眼可见、可以当场纠正。可见性把不可监督的自觉变成可监督的行为，
执行率显著上升（从"隐性跳过"变成"显性暴露"）。

### 5.2 动作类型 → 领域映射（不依赖具体触发词）

bash 类错误靠触发词（ls/grep/`$`）能兜住，但错误来源不止 bash——还有代码、配置、API。
所以元规则不绑定词表，改成**按动作类型查对应领域**：

| 动作 | 查哪些领域 |
|---|---|
| 执行 shell/命令 | [bash] [shell] [命令] [Windows] |
| 写代码/改文件 | [语言] [编码] [脚本] |
| 装包/改配置 | [安装] [配置] [依赖] |
| 调工具/API/MCP | [工具] [平台] [配额] |
| 路径/跨系统传文件 | [路径] [MSYS] [WSL] |

### 5.3 铁律区动态晋升

常驻文件里的 ≤5 条铁律**不写死**，规则是：错题本中频率最高/最痛的条目自动晋升到铁律区，
新晋的挤掉旧的。保证常驻区永远反映**当前**最痛的问题，且随积累自动换血，
不需要每次手动维护。沉淀 → 晋升 → 修剪，形成闭环。

### 5.4 诚实的定位

机制能显著降低"跳过核对"的概率，但模型的概率本质决定**做不到 100%**。
因此价值排序是：**沉淀（确保下次能搜到）> 常驻铁律（覆盖最高频）> 自觉核对（尽力而为）**——
不要指望最后一条兜住全部，但三条合起来把重复犯错的概率压到很低。

## 6. 渐进式积累 + 修剪，防止清单腐烂

- **沉淀时机前置**：不等犯错。用户直接纠正、用户提供他处案例，同样沉淀。
- **同类合并**：同类错误第二次出现时扩充已有条目（加示例/变体），不新建——
  避免 50 条"长得一样"的禁则。
- **定期修剪**：合并重复、删除过时、把"已经内化"的条目降级或删除。
  目标：错题本永远是对当前最痛问题的**有序清单**，而不是错误流水账。

## 6. 成本收益总结

| 项目 | 不采用 | 采用本方案 |
|---|---|---|
| 单次同类错误 | 每次多花 2-5 倍 token + 时间 | 不犯错，零成本 |
| 跨会话 | 每会话可能重犯（记忆检索不到"写之前"） | 元规则常驻，每次动手前触发核对 |
| 常驻成本 | 0（但事后成本无限） | 每 turn 约 30-60 token（元规则 + 铁律区） |
| 规则维护 | 无结构，写哪算哪 | 双层隔离 + 渐进沉淀 + 修剪 |

**一句话：用每 turn 几十 token 的常驻成本，换掉每类错误无限次重犯的事后成本。**
